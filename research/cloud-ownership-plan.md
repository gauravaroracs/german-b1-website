# Cloud ownership and legacy data

Decision, 24 November 2026: older unscoped browser data stays local. The learner can preview it and explicitly choose whether to import it into the currently signed-in account. The local code isolates account data and offers a read-only preview, account comparison and export; direct import and conflict resolution are not implemented yet.

## Current behavior and hazards

The deployed version uses the same local keys in browser-only mode and for every account; cloud reads and automatic uploads can affect that shared data. In the local code, each account has separate keys and pending changes survive reload. Existing backup exports serialize the currently displayed state; imports write individual keys and are not transactional. The local code rejects writes based on stale sql.js snapshots, but error handling and real cross-tab verification remain incomplete.

## Required implementation

1. Bind each mounted app and its storage operations to an immutable account identity. Invalidate the old binding on auth change and remount only after the new binding is ready. Keep browser-only data in its current unscoped keys; use a separate encoded namespace for each account. Never read unscoped data as an account fallback or upload it automatically. Keep personal API keys local and exclude them from imports.
2. Commit a pending mutation or deletion together with its account-scoped value before acknowledging a local save. On restart, do not hydrate over a pending value. Compare against a recorded remote version before replaying a failed write; retain both versions and surface a conflict when safe automatic resolution is not possible. Handle network failures separately from absent cloud records.
3. Offer a preview of the older local data, naming the destination account, categories, counts and conflicts. Provide a way to export the legacy snapshot first. Require an explicit choice for replacements, preserve the original local snapshot, and make the import atomic or safely resumable. Do not mark a partial import as complete.
4. State clearly which scope a backup covers and prevent account changes during restore. Address concurrent-tab writes before claiming they are safe; preserve data if a concurrent change is detected.

## Verification before release

Use isolated browser storage and a mocked cloud service. Test legacy data with empty and populated accounts, two accounts on one browser, sign-out/sign-in and account changes during delayed reads and writes, offline edits and deletions across reload, concurrent remote edits, import conflicts and interruption, backup/restore and two tabs. Verify live Supabase only with authorized isolated test data. Production currently retains the old behavior until a separately authorized deployment of a verified fix.

Implementation checkpoint: local SQLite now has a compare-and-set batch primitive that checks source and destination values and commits all changes together. Tests cover mismatches, aborted commits and stale snapshots. It is not connected to an import flow and does not itself preserve overwritten data, bind a session or check a remote version.

Import-plan checkpoint: a local-only planner validates selected categories, requires explicit replacement of differing account values, rejects pending changes and prepares one atomic batch with the browser source, a pending account copy and a recovery record containing the previous local and observed cloud values. It is not connected to the UI or cloud. The current server uses client-controlled timestamps and unconditional writes, so read-then-write cannot guarantee conflict safety. A production-ready design needs server-managed revisions, deletion history, conditional transactions, idempotency, and a plan for old clients; no migration has been applied or authorized.

Further groundwork: a local staging service rechecks the observed cloud values before the atomic local batch and never uploads; the server can still change after that check, so it is not sufficient for safe sync. The draft `20261124160000_versioned_state_batch.sql` adds a revisioned, idempotent batch RPC and tombstones. An isolated PostgreSQL test covered conflicts, retries, account separation, denied legacy writes and concurrent absent-key writes. The draft intentionally revokes old direct writes and would break existing clients; the current app does not yet use its RPC. Production grants, rollout order, old-client handling and idempotency-record retention require review before any deployment.

The local `versionedStateClient.js` adapter prepares immutable request IDs and bodies, validates RPC responses, and reports uncertain outcomes. It is not wired to app storage; persistent outbox, authenticated owner binding, tombstone reads and user conflict resolution remain required. Tests use a mocked RPC, not Supabase.

The local `versionedOutbox.js` now persists one owner-scoped request before sending and preserves it on conflicts and uncertain outcomes. A confirmed response becomes a durable receipt that must be reconciled with local state before the next request. The caller must supply an authenticated session guard and atomic reconciliation. The outbox is not wired to the app; real-browser concurrency and live Supabase remain unverified.

The local `versionedReconcile.js` validates receipts and preserves edits made after a request was staged. It requires every staged account record to contain a server base revision, a durable mutation ID and an in-flight request marker. Current writers do not yet record those fields, so reconciliation fails closed and is not integrated. The app's existing cloud warnings now track errors per record and notify the UI; pending items are only discovered as they are read, and live cloud behavior remains unverified.

The outbox now atomically stages its request and matching in-flight markers; a versioned mutation helper preserves the marker when a later edit is made. Mocked integration tests cover staging, a later edit and receipt reconciliation. Current app writers still do not create versioned records or use this path, and the draft migration remains undeployed.

An experimental owner-bound versioned storage adapter now covers revision reads, local pending changes, explicit sync and receipt reconciliation in mocked tests. It is not a drop-in: personal API keys, scheduling, conflicts and migration of existing records still need integration. The draft RPC and client now pass an expected account ID; the server rejects a mismatch with the authenticated user before writing. Isolated PostgreSQL tests covered the owner check. The migration remains undeployed and would stop old direct writers.

The draft protocol now also uses a server-guarded read RPC so an account switch cannot appear as an empty account. The adapter can enumerate pending records from an explicit key list and an experimental scheduler resumes receipts and requests, serializes sends, and pauses on conflicts or errors. Mocked tests and isolated PostgreSQL checks pass. These pieces are not wired to the app: existing unversioned account records need a non-destructive migration, conflict rejection needs an atomic recovery transition and UI, and API-key handling and session binding still need integration. No flag is enabled and no migration was applied to production.

The local outbox now records a definite rejected conflict on the affected record and atomically releases the batch markers, while uncertain responses retain the original request for retry. The scheduler can later sync unrelated pending keys while continuing to report unresolved conflicts. A local-only API-key wrapper and mocked component-integration tests were added. Conflict resolution UI, migration of existing account records, app wiring, real-browser tests and live cloud remain open.

The app now has an opt-in experimental path only for a Vite development build with `VITE_EXPERIMENTAL_VERSIONED_SYNC=true` and a loopback Supabase URL. It uses a separate IndexedDB database with legacy migration disabled. The default and production builds do not enable it. Helpers can preview and resolve a conflict with a recovery record, and migrate a clean account record matching the guarded cloud read; neither is connected to a user-facing flow. The experimental path, SQL migration and conflict handling require real isolated browser and backend tests before release; the migration still revokes old direct writers.

The experimental path now exposes a conflict dialog that compares browser and cloud copies and requires an explicit choice. A write barrier waits for active app writes and blocks new ones during resolution; a failed local write prevents resolution until reload. A synthetic fixture was visually checked at 390 and 1440 pixels, and unit tests cover the barrier. This does not verify keyboard interaction, an actual app conflict, local-backend sync or live cloud. Account-record migration and legacy import still lack user-facing controls.

Experimental legacy import now supports selecting categories and explicitly confirming each differing account value. It rechecks the reviewed source and server revision, stages pending records in the isolated account database, and stores the exact reviewed source plus previous account/cloud values for recovery. The source and destination databases cannot share a transaction; a later source edit remains in the original database but may not be part of the reviewed snapshot. Synthetic selection layouts were inspected at 390 and 1440 pixels; real app import, keyboard, local backend and cloud verification remain open. Existing unversioned account migration still lacks UI.

An adversarial review identified a React-effect race during the write pause, a stale cached source reread, and nullable values misclassified against cloud tombstones. The local code now detects writes attempted during a pause before automatic reload, reopens the source for preview/export checks, and marks tombstones as different. The selection UI can expand the browser and account values. Integration tests use real SQL.js with mocked IndexedDB and cloud, including restart and conflicts; real browser interaction and Supabase remain unverified.
